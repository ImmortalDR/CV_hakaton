# Git и размещение кода

Целевой remote: `https://github.com/ImmortalDR/CV_hakaton.git`.
Workspace и корень собственного проекта: `/root/hakaton`.

При подготовке комплекта репозиторий был доступен, публичен; GitHub вернул пустой список веток и размер 0. Это снимок состояния, не основание считать репозиторий пустым при будущем запуске.

1. Проверь текущий `git status`, корень рабочего дерева и remotes. Сначала прочитай существующие `AGENTS.md` и пользовательские изменения. Не выводи credential helpers, токены или URL с секретами.
2. Если git уже настроен правильно, продолжай его. Не делай вложенный репозиторий. Если каталог не является репозиторием, инициализируй его без удаления файлов, добавь origin, проверь удалённые ветки. Если удалённая история уже появилась, получи её и интегрируй аккуратно; не перезаписывай локальные файлы принудительным checkout/reset.
3. При пустом remote создай начальную историю собственного проекта. Веди разработку в ветке `codex/fsp-mvp` или свободной аналогичной. Существующую ветку с чужими изменениями не переименовывай и не заменяй.
4. До первого добавления проверь `.gitignore`. Исходные PDF/PPTX, transcription, большая подборка, промежуточный аудит, архивы, веса, секреты, локальные зависимости и реальные персональные данные не добавляются автоматически. Готовые демо-презентация/документация в `demo/` и `docs/delivery/` допустимы, если не содержат лишних данных.
5. В репозитории должны быть все файлы, необходимые для запуска собственного приложения: код, миграции, lock-файлы, тесты, безопасные демо-данные, документация, используемые фрагменты и лицензии. Приложение не должно читать исключённую папку исходников в runtime.
6. Делай осмысленные коммиты после законченных изменений. Перед каждым проверяй staged diff; команды вида `git add .` без просмотра содержимого не заменяют проверку.
7. После соответствующих проверок отправляй изменения в рабочую ветку origin. Не используй force-push, не меняй защиту веток и не удаляй чужие ветки. Не объединяй в защищённую основную ветку автоматически.
8. В финале укажи ветку, commit, результаты проверок и состояние push. Если аутентификация недоступна, сохрани локальные коммиты и продолжи разработку; сообщи конкретный оставшийся шаг, не изображая успешную отправку.

Не включай в коммиты секреты из окружения и не записывай их в журналы. В этот архив `.git` и доступ к аккаунту не помещены. Сам факт доступности репозитория в текущем чате не гарантирует, что будущий сервер Codex уже авторизован.
