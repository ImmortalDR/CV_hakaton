## 2 Опубликовать код и правильно использовать резервный bundle

**Остаток Pck2. Ответственный: Данила и участник с доступом к GitHub.**

1. Проверить актуальный remote и сохранить чужие незакоммиченные изменения. Не применять reset --hard, force-push и очистку рабочего дерева.
2. Обеспечить обычную публикацию проверенных коммитов. Handoff фиксирует отсутствие авторизации на сервере; сама доступность чтения GitHub не означает наличие прав push.
3. Проверить опубликованный SHA, README, FOR_JURY, PDF/DOCX, презентацию и ссылки из SUBMISSION_LINKS. Не оставлять в актуальной инструкции заявление «push ещё не выполнен» после его успешного выполнения.
4. Проверить необходимые untracked-файлы перед включением в сдачу. Этот план и handoff не входят автоматически в старый bundle; локальные файлы не возникают на GitHub от отправки только старых коммитов.
5. Если после проверенной версии были изменения приложения, сверить и при необходимости обновить API, web и worker; выполнить только обоснованную регрессию. Отдельный деплой без изменения приложения не нужен.

**Уточнение инструкции handoff:** файл `local-backups/stage-a-20261021/codex-fsp-mvp-stage-a.bundle` проверен командами `git bundle verify` и `git bundle list-heads`. Он исправен, содержит ссылку **HEAD** на `889ebf38a743d68860cf298dc11b288e2142993e` и требует базовый коммит `2e6d6daa5bfb59f6d5a7e7317aa41093c8f05980`. Это инкрементальная резервная копия, не самодостаточный полный клон и не доказательство публикации.

Оставшаяся документационная правка: исправить пример handoff, который пытается импортировать отсутствующую в bundle ссылку `refs/heads/codex/fsp-mvp`. На машине с базовым коммитом использовать отдельную свободную ветку, например:

```bash

git fetch /path/to/codex-fsp-mvp-stage-a.bundle HEAD:refs/heads/review-stage-a-889ebf3
```

Далее сопоставить историю с текущей удалённой веткой и интегрировать обычным безопасным способом, не сбрасывая чужую работу. Эта операция при обновлении плана не выполнялась: здесь исправлена только инструкция для оставшейся работы.

## 3 Пройти человеческую приёмку и завершить передачу

Перед проходом обеспечить подходящие аккаунты:

- новый кандидат без ФСП для первого теста;
- кандидат с готовым подтверждённым уровнем для быстрого подбора;
- приглашающая компания и другая компания без согласия;
- отдельный кандидат для нового SQL Middle и проверки округления;
- сценарий заданий и отзыва доступа.

Десять аккаунтов 20 октября уже использованы аудитом, review-аккаунты общие. Не считать их чистыми и не сбрасывать историю/кулдауны. Проверка трёх входов в smoke не доказывает доступность каждого ручного сценария. В текущем human-протоколе SQL Middle предложен общему кандидату: если специализация уже закреплена, назначить отдельный data-аккаунт; не оставлять обязательный шаг непроходимым.

Маршрут: **тест → результат → публикация → доказательства у работодателя → подбор → приглашение с зарплатой → принятие → контакты → диалог**. Затем другая компания, PDF до/после согласия, отзыв доступа, старая подборка после нового запроса и мобильный экран.

Оценить то, что не закрыто селекторами: понятность предупреждений и ошибок, различимость анонимов, объяснимость баллов, компактность формы, читаемость PDF и слайдов. Проверить сайт с внешнего устройства/сети. Записать время и места остановок. Внутреннюю приёмку не называть независимым бизнес-пилотом.

По Q6 человек фиксирует решение: достаточно управляемого времени и live pause/resume либо назначается календарная проверка. Реальную неделю не объявлять наблюдавшейся и не делать обязательным ожиданием без обоснования.

После актуального push и PASS обязательных шагов подготовленный текст SUBMISSION_LINKS передаёт организаторам уполномоченный участник. Записать дату, канал и подтверждение. **Pck5 до факта передачи остаётся незакрытым.**

### Ошибки полей B07

- Проверять содержимое после удаления крайних пробелов.
- Не отправлять пустое сообщение из пробелов.
- Давать конкретную подсказку рядом с некорректным полем имени, компании, сообщения или другого обязательного значения.
- Сохранять корректные данные остальных полей и текст при исправимой ошибке.
- При нескольких ошибках переводить фокус к первой; убирать исправленную ошибку.
- Общий баннер использовать для общих ошибок сервера и соединения.
- Проверить дополнительный сценарий закрытия чата при ошибке отправки: ошибка валидации или сети не должна очищать переписку и изображать отзыв доступа. Текст сообщения при исправимой ошибке сохраняется.

### Зарплатная вилка U05

Сократить повторяющиеся объяснения, оставив одно основное действие и короткую подсказку. Полные правила сохранить доступными по запросу. Для ожидания пересдачи полезно показывать оставшееся время, не заменяя точную дату недостоверным счётчиком.

Оценить оставшуюся длину пути от уже упрощённой формы к результатам; при необходимости добавить сворачивание с резюме запроса. Проверить зоны нажатия, модальные окна и экранную клавиатуру. Это контроль отсутствия ухудшения на данных примерах, а не доказанный рост качества найма или оптимальность весов.

Создать отдельный версионированный набор, способный различать варианты формулы. Включить случаи:

1. Все обязательные навыки подтверждены, общий тест ниже.
2. Тест выше, один обязательный навык не проверен.
3. Сильные достижения ФСП при более слабом тесте.
4. Одинаковые доказательства, разная самооценка или стаж.
5. Отсутствие истории ФСП.
6. Проваленный навык против непроверенного.
7. Несколько обязательных требований.
8. Отсутствие полных совпадений.
9. Несколько допустимых грейдов.
10. Равные итоговые баллы и стабильность порядка.

До сравнения определить ожидаемое поведение и основания меток. Независимых разметчиков не предполагать; авторскую разметку называть авторской. Проверка сценариев разработчиками допустима как инженерная, но не как внешняя сертификация.

Помимо P@5 показать изменившиеся пары и позиции, долю неполных совпадений наверху, выполнение правил монотонности. - Не раскрывать эталоны активного теста и контакты без согласия, не менять грейд бонусом ФСП и не понижать его автоматически при провале.
- Не публиковать секреты. Не выдавать симуляции за людей, внутреннюю проверку за независимую экспертизу, bundle за push.
- Не копировать старые PASS под новые версии. Сохранить доказательства коллеги; повторять проверки по изменениям и рискам, а не ради переписывания истории.

Итог дальнейшей работы: актуальный статус каждого остатка, коммиты, push/деплой, реальные проверки и артефакты, заполненный человеческий протокол, честные ограничения и факт сдачи. Само обновление этого плана не меняет код продукта и не означает выполнения оставшихся задач.
