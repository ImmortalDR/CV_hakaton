## Находки и рекомендуемые изменения

### F1. P1 — неполные совпадения остаются основной выдачей

Основания: FTT.2, ТЗ §6.1; `apps/api/fsp/matching.py:68`,
`apps/api/fsp/main.py:833`, `apps/web/src/App.tsx:1619`.

`eligible()` проверяет специализацию, грейд и ФСП, но не обязательные навыки.
`rank_candidate()` начисляет баллы за met, оставляя unknown/unmet в выдаче.
Воспроизведено на замороженном test: обязательный React → пять результатов,
ноль релевантных, P@5=0. При Python + testing полностью подходят два из пяти,
P@5=0,40. UI честно показывает неизвестные основания, поэтому это не скрытое
присвоение доказательств, а слабая политика рекомендации.

Предлагается основной список «Все обязательные требования подтверждены»,
отдельный раскрываемый список частичных совпадений и явное состояние
«Подтверждённых соответствий пока нет». Пользователь должен понимать,
что relax-фильтр меняет условия. Не подменять unknown на unmet.

Критерий проверки: ноль основных рекомендаций для невозможного обязательного
React; две основные для контрольного запроса Python + testing. При этом
фиксированный знаменатель P@5=5 оставит второму запросу 0,40 даже после
исправления. Дополнительно измерять долю нарушения обязательных требований,
полноту выдачи и корректный отказ; не обещать автоматический рост P@5.
Старый test после использования для исправлений становится регрессионным:
итоговое улучшение измерять также на новом, заранее отложенном наборе.

### F2. P1 — PR.1 закрыт не полностью

Основание: B4; `evaluation/run.py:68–123`.

Действительно есть многократная оценка одной синтетической персоны. Но
`variant_stability` — доля наиболее частого исхода, не доля совпадающих
результатов двух прохождений. Опубликованные 97,92% корректны как согласие
с эталоном / модальная доля, но не должны подписываться другим показателем.
По всем парам уже сохранённых 20 исходов на персону получено 2191/2280 =
96,10% совпадений. Это дополнительный описательный расчёт на тех же
синтетических данных; пары зависимы, это не 2280 независимых испытуемых.

Кроме того, текущая симуляция определяет максимальный пройденный уровень
за три отдельных теста, а пользователь выбирает конкретный уровень.
Нужен явно описанный test-retest выбранной категории/грейда и исхода
подтверждения с отдельным тестом сохранения ранее подтверждённого уровня.
Отдельной статистики разделяющей силы по заданиям/семействам нет.

Предлагается заранее задать слабые/средние/сильные синтетические профили,
включая частичное знание, случайные ошибки и пограничные случаи; сохранять
ответы по каждому заданию. Измерить повторную согласованность, переходы,
частоту успеха в независимых группах и разницу между сильной и слабой
группами. Не определять силу кандидата результатом того же оцениваемого
задания. Показать низкоразделяющие семейства и ограничения симуляции.
Пилот с людьми полезен, но B4 прямо разрешает синтетику для хакатона.

### F3. P1 — слабое разнообразие и пороги подтверждения навыков

Основания: VS.1, VS.5, FTT.4, ТЗ §6.2;
`apps/api/fsp/bank.py:19`, `:140`, `:157`.

В категории всегда два фиксированных семейства × два задания. Генерируются
разные числа и правильные ответы, но не разные семейства/порядок. Это снижает
пользу распространения конкретных ответов, однако мало защищает от
заучивания двух способов решения. Это риск достаточности механики, а не
утверждение, что выдаются буквально одинаковые тексты.

Воспроизведено: Python Senior, три верных ответа из четырёх → тест пройден,
при этом Python 1/2 = unmet, HTTP 2/2 = met. Так устроены существующие разные
пороги общего результата и навыка; это описано в ASSESSMENT.md. Серверной
подмены нет, но доказательность профессионального грейда слаба. Четыре
числовых задания особенно ограничены как подтверждение Senior.

Также Docker и React есть среди восьми выбираемых навыков, но отсутствуют
во всех семействах банка: подтвердить их обычным путём невозможно.

Предлагается расширить семейства внутри существующих шести категорий,
собирать вариант по компетенциям, добавить обязательное подтверждение
ключевого навыка для присвоения уровня. Для непокрытых навыков либо добавить
проверенные задания, либо явно обозначить отсутствие проверки и не обещать
подтверждённый поиск. Изменения должны иметь новую версию рубрики;
не понижать автоматически ранее подтверждённые грейды.

навыка или основанием присвоения грейда. До реализации прямо подписать,

## Приоритет относительно набора данных

Предыдущий промпт Perplexity полезен для проверки подбора (критерий 35%),
но не закрывает PR.1 и тестирование (25%). Нужны два отдельных набора:
пары потребность–кандидат с разметкой и профили компетенций/ответы на варианты
для проверки грейдов. Большой корпус резюме не заменяет второй набор.
Источник ответов прямо допускает синтетику и не требует внешних экспертов
как условия MVP; реальную независимую проверку можно развивать отдельно.

Порядок работ: F1 → F2/F3 → F4/F5 → F6/F7. Регулярные задания (E09),
дополнительные категории и дизайнерские роли — после основного качества.
Документ ATS и актуализацию ссылок можно делать независимо от основного кода.
