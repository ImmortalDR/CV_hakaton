# Следующий этап задач Тимофея: банк 2.0.0

9 октября 2026, Москва. Работа Codex по поручению Тимофея Розова.
Основание: продолжить оставшиеся исследовательские задачи после отчёта
TIMOFEY_RESEARCH_2026-10-09.md. Экспертную подпись или участие людей не имитируем.

## Реализация

Банк расширен с 12 до 24 семейств: четыре на каждую из шести категорий.
Вариант содержит восемь вопросов — два на семейство. Добавлены индексы Python,
изменяемые аргументы по умолчанию, LRU, мутант abs, фиксированные лимиты API,
управляемые повторы, NULL/COALESCE, GROUP BY/HAVING, оконные суммы, условная
доля, среднее после исправления данных и optimistic locking.

Рубрика до измерения зафиксирована в evaluation/BANK_V2_PROTOCOL.md:
6/8 и минимум 3/4 по основному навыку. Теперь одна ошибка core допустима,
две не скрываются хорошими ответами по вспомогательной теме. Балл точный:
7/8 = 87,5%, а не округлённые вниз 87%. Сервер выдаёт рубрику конкретной
попытки; интерфейс отображает её и фактическое число вопросов.

Воспроизводятся старые генераторы 1.1.0 и 1.2.0; fingerprints заморожены по
коммитам 0a5b796 и 1afef6e и сверены для всех категорий. Старые активные попытки
оцениваются своей рубрикой, результаты/грейды прошлого не меняются. Для 1.0.0
сохранено оценивание записанных вопросов, повторная генерация не обещается.
Ответы с номерами вне конкретной попытки отвергаются. Лимит API расширен до 8.

Сборщик датасета 1.0.1 принимает дробный score; опубликованные архивы 1.0.0
не менялись. Старые оценочные скрипты закреплены за прежними банками, поэтому
старые метки и результаты не выдаются за оценку нового содержания.

## Содержательное ревью и границы покрытия

Проход 1: прочитаны собственные bank/matching/outputs/schemas, независимые
решатели и оценочные скрипты, предыдущий отчёт и рабочие инструкции.
Проход 2: прослежены версия → сохранённые вопросы → валидация ответов → оценка
→ доказательства/профиль → UI, а также новые результаты → схема датасета.
Проход 3: проверены совместимость, частично верные ответы, пустые/чужие вопросы,
неизменность старых форм, поля API до сдачи и смысл заявляемых метрик.

Собственные новые файлы прочитаны целиком. В main.py/App.tsx/seed.py прочитаны
затронутые цепочки. Полный сторонний архив заново не читался; старые ограничения
coverage остаются. Готовые библиотеки не переоцениваются на основании названий.
Новые эталоны проверяются альтернативным алгоритмом, реальным functools.lru_cache
и SQL в SQLite. Это проверка корректности задач, не экспертиза профессионального
содержания и не испытание всех версий PostgreSQL/SQLite.

## Сравнение на заранее заданных моделях

200 dev-вариантов/категорию для выбора частого ответа семейства, другие
500 probe-вариантов для оценки. Порог не менялся после просмотра результата.
Две версии × шесть категорий × 500 вариантов × семь стратегий = 42000
симулированных попыток. Независимых сверок эталонов 36000, расхождений 0.

| Стратегия | Доля успеха 1.2.0 | Доля успеха 2.0.0 |
|---|---:|---:|
| Самый частый ответ семейства, выбранный на dev | 2,50% (75/3000) | 0% (0/3000) |
| Знание только старых двух семейств | 100% | 0% |
| Знание всего, независимая ошибка 10% на вопрос | 79,97% | 92,60% |
| Знание всего, независимая ошибка 20% на вопрос | 59,33% | 71,40% |

Положительная/отрицательная детерминированная разметка совпала с результатом
во всех случаях. Идеальное разделение strong/weak заложено в симулятор и не
является доказательством дискриминативности на людях. Попарное совпадение
исходов при шуме 20% выросло с 51,67% до 59,14%, при шуме 10% — с 67,95% до
86,28%. Пары зависимы. Точный перебор масок верных ответов даёт при p=0,8
вероятность успеха 0,6144 → 0,7340032; это проверка вероятностной модели.

Даже 0/500 в отдельной категории даёт верхнюю 95% границу Wilson около 0,76%
в данном процессе генерации/угадывания. Заучивание общего решения, утечка
семейств, помощь LLM и реальная сложность не измерены этой стратегией.
Профессиональные Junior/Middle/Senior, 30 минут и сам порог ещё не калиброваны
на людях. Ширина содержания улучшена, но восемь числовых задач остаются узким
измерением. Docker/React по-прежнему не подтверждаются этим банком.

## Подготовка человеческой проверки и выступления

- evaluation/pilot.py создаёт 12 неизменяемых форм A/B без ответов,
  отдельные ключи с правами 0600, пустые participants.csv/responses.csv,
  таблицу содержательного ревью 24 семейств и SHA-256 манифест.
- Расчёт принимает только реальные введённые строки; требует источник
  независимой метки, если она задана, не заменяет пропуски правильными ответами,
  отвергает дубли, неполные попытки и повреждённые формы.
- Считает матрицу ошибок, согласие с независимыми метками, согласие A/B
  по людям и разность долей правильных ответов независимых групп по семейству.
- Пустой комплект проверен: not_run, 0 участников/попыток, показатели null.
  Тестовые искусственные строки для проверки инструмента не входят в пилот.
- Инструкция: docs/delivery/HUMAN_PILOT.md. Подготовлены RESEARCH_V2.pdf и
  RESEARCH_V2.docx с кратким объяснением методики и формулировкой для питча;
  исходный шаблон презентации и существующая командная презентация не перезаписаны.

Для внешнего пилота нужны участники и независимые содержательные заключения.
Для реальной почты нужен SMTP-провайдер/конфигурация; пользовательский демостенд
не переключался на внешнюю рассылку. Эти зависимости не объявляются решёнными.
