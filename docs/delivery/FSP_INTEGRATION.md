# ФСП ID и будущий Keycloak

В текущем MVP `fsp_provider.py` отделяет интерфейс Provider от DemoProvider.
Пользователь выбирает вымышленный пример победителя или участника. Ответы
помечены `provider=demo_fsp`, `verification=simulated`. Это не подтверждение
реестром и не реальный FSP ID. Идентификатор примера дополнен локальным ID
пользователя, поэтому не подменяет глобальную внешнюю идентичность.

DEMO_MODE=false запрещает демонстрационную привязку. Без привязки работают
профиль, тест, подбор, приглашение, раскрытие контактов и диалог. Отвязка
удаляет текущий спортивный бонус, но не меняет грейд и историю тестов.
Историческая подборка сохраняет помеченное доказательство на свою дату.

План реальной интеграции, **не исполненная интеграция**:

1. Получить у ФСП адрес Keycloak issuer, регистрацию OIDC-клиента,
   разрешённые redirect URI, API достижений, scopes и тестовые учётные записи.
2. Вход через Authorization Code + PKCE. Проверять state/nonce, issuer,
   audience, срок и подпись ID token по доверенному JWKS. Не принимать
   переданный браузером ID/статус победителя как доказательство.
3. Привязка внешнего `(issuer, subject)` к локальному User только из
   действующей сессии и после подтверждённого OIDC-перехода. Не объединять
   аккаунты автоматически по неподтверждённому email. Уникальность пары — в БД.
4. Сервер запрашивает достижения по минимально необходимому scope;
   хранит provider, внешний ID события, результат, дату, время проверки
   и источник. Секреты и access/refresh tokens не уходят в браузер и логи.
5. Реализовать отзыв связи, истечение/обновление свидетельства, повторную
   синхронизацию и понятное состояние недоступности внешнего API.
6. Дополнить контракт провайдера, схемы верификации, миграцию и тесты:
   чужой subject, повторный callback, неверные issuer/audience/nonce,
   истёкший токен, подмена достижения, частичная недоступность.

Производственные OIDC-потоки, доступ к реестру и проверка этих интеграционных
сценариев не запускались: конфигурация и внешние учётные данные не предоставлены.
Достижения останутся ограниченным сигналом внутри категории; присвоение
профессионального грейда продолжит зависеть от отдельной процедуры проверки.
