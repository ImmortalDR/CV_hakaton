## Исследования после хакатона: основания для грейдов

Формы 2.1.1 и пустые таблицы подготовлены в `audit/human-pilot-2.1.1-final/`. Провести A/B без раскрытия решений до второй формы, зафиксировать порядок и интервал. Ожидаемую категорию получать независимо от этого теста, с источником. При отсутствии меток оставить согласие с эталоном null. При отсутствии групп оставить дискриминацию null. Даже небольшой внутренний пилот не равен внешней сертификации.

Следующий содержательный эксперимент — практическая отладка API / SQL по схеме с заранее согласованной рубрикой. Не менять пороги и не добавлять субъективные баллы в действующий грейд до получения данных.

## M01: качество на реальных запросах

**Тимофей + бизнес.** [Challenge](MATCHING_CHALLENGE_2026-10-21.md) отличает формулы и проверяет инварианты, но не измеряет качество найма. Зафиксированы решения пользователя: общий балл внутри категории, явные пробелы; старые метки не изменять.

Нужны реальные требования работодателей и независимая оценка полезности кандидатов для этих требований. Оценивать по запросам, не считать кандидатов одного запроса независимыми наблюдениями. Только после появления подходящих порядковых меток применять NDCG; запросы без подходящих людей оценивать отдельно. Не объявлять статистически убедительный прирост на 8 запросах. Реальные отклики из других датасетов не становятся объективными метками навыков автоматически; их происхождение и ограничения должны сопровождать отдельное исследование.

## Производительность и эксплуатационные ограничения

**Данила.** N+1 и найденный конкурентный сбой PDF исправлены, итоговые 270 чтений проходят. Но p95 банка 4,43 с при 30 одновременных полных выгрузках всё ещё требует улучшения перед масштабированием.

- Спроектировать пагинацию/лимит выдачи с сохранением группировки и стабильного порядка; проверить, что история и фильтры остаются понятными.
- Измерить нагрузку с входом и записью, распределение реальных размеров банка, длительный прогон и ресурсы. Текущий прогон — 14,78 с, не soak test.
- При росте нагрузки PDF — отдельная очередь/процессы после измерения. Текущая процессная блокировка устраняет гонку, но ограничивает параллелизм.
- Для чата при потере ответа после фактической записи полезен idempotency request_id: сейчас ручной повтор может создать дубликат. Это выявленное ограничение механизма повторов, не доказанный сбой в успешном прогоне.
- Длительное календарное наблюдение 7/24/90 дней не проводилось. Для хакатона сохранены проверки управляемым временем; реальное ожидание недели не заявляется.
- Установка из исходников/образов и новая БД проверены; полностью автономный архив без сети не проверялся. Тестовые БД fsp_finalcheck_* оставлены, глобальная очистка Docker не допускается.
