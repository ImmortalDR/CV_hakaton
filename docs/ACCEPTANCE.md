# Приёмка MVP

Статус всех пунктов на момент подготовки комплекта: предстоит реализовать и проверить. Сохраняй фактические результаты в `docs/delivery/VALIDATION.md`; отмечай `pass / fail / not_run`, а не только галочки в плане.

## Обязательные сценарии

1. Новый кандидат подтверждает почту, принимает согласия, заполняет профиль, выбирает специализацию/грейд, проходит тест и видит объяснённый результат. Русский PDF открывается и не содержит обрезанных полей.
2. Провал первого теста не присваивает низкий грейд; кандидат добровольно выбирает тест ниже. Провал пересдачи не стирает ранее подтверждённый уровень. Проверяются границы выбранного кулдауна и история.
3. Одинаковые ответы при той же версии/seed дают одинаковую оценку. Варианты различаются, сохраняют blueprint, корректны по независимому решению. Изменение payload клиента не меняет балл, seed или грейд. Повторная отправка не создаёт новый результат.
4. Работодатель заполняет компанию, описывает потребность, подтверждает структурированные требования и видит категории/кандидатов с доказательствами. Фильтры работают; прежняя подборка доступна после уточнения.
5. Неизвестный опыт не считается выполненным требованием. Русский запрос, отсутствие навыка, пустой запрос, отсутствие подходящих кандидатов и совпадение только по словам обработаны явно. ФСП не меняет категорию и грейд.
6. Кандидат без ФСП проходит весь путь. Демонстрационная привязка добавляет помеченные достижения; они влияют только на позицию внутри категории согласно опубликованному правилу.
7. Работодатель приглашает без публикации вакансии. Нет зарплаты/валюты/описания, отрицательные значения и min>max отклоняются сервером. Принятие/отклонение меняет статус у обеих сторон; повторное действие безопасно.
8. До принятия контакты закрыты в профиле, поиске, объяснениях, PDF и исходных файлах. После принятия доступны только пригласившему работодателю. Второй работодатель по прежнему не видит их; чужой кандидат не читает приглашение. Проверить прямые запросы по чужим ID, а не только скрытые кнопки UI.
9. Если есть прямой отклик: именно он даёт адресное разрешение соответствующему работодателю. Если есть чат: только участники разрешённого диалога получают доступ.
10. Отозванное/отсутствующее согласие на публикацию и настройки приватности реально меняют доступность профиля согласно документированным правилам. Поведение существующих разрешений после отзыва описано отдельно и не меняется случайно.

## Проверка качества

- Приложены данные, происхождение, разметка и описание train/dev/test; наборы и пороги зафиксированы до финального измерения. Нет повторов кандидатов/резюме и скрытой утечки через варианты заданий.
- Для подбора рассчитаны P@5 по запросам, среднее, baseline и разбор ошибок. Для тестов — согласие с эталонным уровнем, матрица ошибок и стабильность на вариантах. Нет подмены реальных замеров чужими Kaggle-результатами.
- Размер выборки и ограничения явно указаны. Маленький пилот не называется доказательством объективности на всём рынке.

## Проверка поставки

- Чистая установка по README, миграции и тестовый набор работают; перезапуск сохраняет данные; демонстрационный reset отделён от рабочих данных.
- Секреты задаются окружением; `.env.example` содержит только безопасные примеры. В git нет токенов, реальных CV/контактов и тяжёлой исходной подборки.
- Сборка frontend/backend, релевантные unit/integration/E2E проверки и браузерный сценарий реально запущены. Указаны команды и среда. Неработающий внешний сервис не скрыт за моками без маркировки.
- OpenAPI соответствует фактическим маршрутам. Есть актуальные зависимости, лицензии и инструкция резервного локального показа.
- Основные операции замерены на указанном оборудовании при десятках одновременных пользователей; необоснованных требований к GPU нет.
- Демо проходит за 3–5 минут; жюри может самостоятельно пройти тест и выполнить приглашение. Есть готовые демонстрационные аккаунты, включая кандидата без ФСП.
- Финальные ссылки: репозиторий, презентация, DOCX/PDF-документация, стенд или допустимая ТЗ замена видео+локальный запуск.
- В презентации обязательные блоки исходного шаблона: команда/задача, суть и уникальность, роли/контакты участников, развитие и трудности; реальные результаты и живой сценарий. Незаполненные сведения о команде перечислены явно.

Релизный отчёт должен отдельно назвать пройденное, проваленное и не запускавшееся. Формулировка «без ошибок» не заменяет эти данные.
