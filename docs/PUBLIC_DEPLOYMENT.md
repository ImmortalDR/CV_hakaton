# Публичное развёртывание: полная инструкция

[Короткий запуск](../README.md). Код приложения находится в ветке `codex/fsp-mvp`.

## Публичный сайт: домен, HTTPS и регистрация пользователей

Инструкция ниже предназначена для **отдельного Linux-сервера с публичным IP**, например VPS с Ubuntu 24.04 LTS. Она использует включённый в проект Caddy; переписывать приложение не требуется. HTTPS-профиль использует сеть Linux-хоста, поэтому эту схему не следует без изменений переносить на Docker Desktop для Windows/macOS.

Результат: посетитель открывает ваш домен по HTTPS, создаёт аккаунт кандидата или работодателя, получает письмо, подтверждает адрес и входит в кабинет. Аккаунты и данные хранятся в PostgreSQL на вашем сервере. Это интернет-развёртывание; автономный комплект для изолированной сети пока не подготовлен.

### 1. Подготовьте сервер и инструменты

Установите Docker Engine вместе с плагинами Compose и Buildx по [официальной инструкции для Ubuntu](https://docs.docker.com/engine/install/ubuntu/) либо [для своей ОС](https://docs.docker.com/engine/install/). Пользователь, выполняющий команды ниже, должен иметь доступ к Docker.

Для Ubuntu/Debian установите остальные инструменты:

```bash
sudo apt-get update
sudo apt-get install -y git python3 curl ca-certificates
sudo systemctl enable --now docker
docker version
docker compose version
```

На сервере должны быть свободны TCP-порты **80, 443, 3080 и 5547**. Первые два используются публичным HTTPS-прокси; последние два — только на loopback для сайта и БД. Проверьте занятые порты:

```bash
sudo ss -ltnp
```

Если 80/443 уже занимает другой сайт или reverse proxy, не останавливайте его вслепую: понадобится отдельный сервер либо интеграция с существующим прокси. У проекта фиксированное Compose-имя `fsp-mvp`; вторую копию на том же сервере нельзя запускать по этой инструкции без разделения имён, портов и томов.

### 2. Настройте домен и сетевой доступ

В примерах **`jobs.example.org` — заглушка**. Замените её в `.env` и проверочных командах своим доменом, например `career.your-company.ru`.

- Создайте DNS-запись **A** домена на публичный IPv4 вашего сервера.
- Запись **AAAA** добавляйте только при рабочем IPv6 до этого сервера; ошибочная AAAA может помешать доступу и выпуску сертификата.
- Разрешите входящие **TCP 80 и 443** в firewall сервера и правилах сети/VPS. При NAT настройте перенаправление этих портов на сервер.
- Сохраните доступ по вашему SSH-порту. **Не открывайте наружу 3080, 5547 или 5432**: посетители должны обращаться через HTTPS-прокси.
- Серверу нужен исходящий доступ к DNS, GitHub, репозиториям образов/пакетов, ACME-сервису Let's Encrypt и вашему SMTP-серверу.

Если UFW уже используется, добавить правила сайта можно так (правило вашего SSH-доступа должно сохраняться):

```bash
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw status
```

Эти команды не включают выключенный firewall; правила в панели провайдера настраиваются отдельно. Проверьте разрешение домена:

```bash
getent ahosts jobs.example.org
```

В этой инструкции домен должен указывать непосредственно на сервер. При использовании внешнего CDN/прокси дополнительно согласуйте его настройку с выпуском сертификатов Caddy. Условия автоматического HTTPS описаны в [документации Caddy](https://caddyserver.com/docs/automatic-https).

### 3. Получите код и создайте настройки

Для новой публичной установки выполните **на сервере**:

```bash
git clone --branch codex/fsp-mvp https://github.com/ImmortalDR/CV_hakaton.git
cd CV_hakaton
python3 scripts/configure.py
chmod 600 .env
```

Пока не запускайте Compose: сначала отключите деморежим и настройте почту. Скрипт создаёт случайный пароль PostgreSQL и не перезаписывает уже существующий `.env`.

Откройте `.env` текстовым редактором. **Сохраните созданную строку `POSTGRES_PASSWORD`**, остальные параметры приведите к следующему виду. Каждая переменная должна встречаться один раз:

```dotenv
DEMO_MODE=false
PUBLIC_URL=https://jobs.example.org
BIND_ADDRESS=127.0.0.1
COOKIE_SECURE=true
COMPOSE_PROFILES=https
HTTPS_HOST=jobs.example.org
HTTPS_SITE_ADDRESSES=jobs.example.org
SMTP_HOST=smtp.your-mail-provider.example
SMTP_PORT=587
SMTP_TLS=true
SMTP_USER=your-smtp-login
SMTP_PASSWORD='replace-with-your-smtp-password'
SMTP_FROM=noreply@your-company.ru
```

`PUBLIC_URL` указывается с `https://`, без завершающего `/`; `HTTPS_HOST` и `HTTPS_SITE_ADDRESSES` — только имя домена, без схемы и пути. Не копируйте домен, IP или почтовые реквизиты нашего демонстрационного стенда.

SMTP-реквизиты возьмите у своего почтового провайдера/администратора. В текущем коде поддержан **SMTP с STARTTLS**, обычно порт **587**; порт 465 с неявным TLS этой реализацией не поддерживается. `SMTP_FROM` должен быть разрешён для отправителя. Если провайдер требует пароль приложения и настройку SPF/DKIM, выполните его инструкции.

Одинарные кавычки в `.env` позволяют сохранить `$` в пароле без подстановки Compose; для других специальных символов используйте [правила синтаксиса `.env`](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/#env-file). Не публикуйте `.env`, пароли и ссылки подтверждения. Не запускайте `source .env`: это файл настроек Compose, а не shell-скрипт.

`DEMO_MODE=false` отключает общие демовходы и автоматическое создание демонстрационных профилей. **Уже существующие демозаписи не удаляются.** Если ранее на этом сервере запускался локальный демостенд, его БД сохранится. Для чистой публичной установки используйте отдельный сервер/подготовленную отдельную БД; не удаляйте том с нужными данными.

### 4. Соберите и запустите

Из каталога с `compose.yaml` и `.env`:

```bash
docker compose config --quiet
docker compose up -d --build --wait --wait-timeout 180
docker compose ps
```

`config --quiet` проверяет конфигурацию без вывода секретов. Сборка в первый раз может занять несколько минут. При старте API автоматически применит миграции; с `DEMO_MODE=false` демоданные не добавляются.

Запустятся пять сервисов: `db`, `api`, `web`, `task-worker`, `edge`. У `db`, `api`, `web` и `edge` ожидается состояние `healthy`, у `task-worker` — `running` (отдельной healthcheck у него нет). Caddy получает сертификат Let's Encrypt, перенаправляет HTTP на HTTPS и обслуживает продление. Он должен оставаться запущенным с сетевым доступом; состояние сертификатов сохраняется в Docker-томах.

Если ожидание завершилось по таймауту, сначала посмотрите диагностику ниже: не удаляйте тома и не повторяйте выпуск сертификатов бесконечно.

### 5. Проверьте доступ и регистрацию

Замените домен и выполните:

```bash
curl --fail --show-error https://jobs.example.org/api/health
curl -I http://jobs.example.org
```

Первый запрос должен вернуть JSON с `status: "ok"` и `demo: false`, без ошибки сертификата. Второй — перенаправление на HTTPS. Не добавляйте `-k`: оно скроет проблему доверия сертификату.

Затем с **другого устройства/сети**, например телефона через мобильный интернет:

1. Откройте `https://jobs.example.org`: должна появиться стартовая страница с входом и регистрацией, без кнопок общего демовхода.
2. Зарегистрируйте кандидата на доступную вам почту. Дождитесь настоящего письма, откройте ссылку и войдите с заданным паролем. Письмо не должно вести на localhost или чужой домен.
3. В другом браузерном профиле зарегистрируйте работодателя и подтвердите его почту.
4. У кандидата заполните профиль, подтвердите уровень тестом и включите публикацию/необходимые согласия. Новый аккаунт сам по себе не получает подтверждённый грейд.
5. У работодателя заполните компанию, найдите опубликованного кандидата и отправьте приглашение с зарплатой. Примите его со стороны кандидата: контакты должны открыться пригласившей компании, диалог — обеим сторонам.
6. Проверьте «Забыли пароль?» на тестовом аккаунте: получение письма, смену пароля и новый вход.

На новой установке до появления опубликованных кандидатов банк может быть пустым — это ожидаемо. Реальные достижения ФСП автоматически не появятся: подключения к официальному реестру пока нет.

### 6. Если что-то не работает

```bash
docker compose ps
docker compose logs --tail=100 edge
docker compose logs --tail=100 api web task-worker
curl --fail http://127.0.0.1:3080/api/health
```

| Симптом | Что проверить |
|---|---|
| Домен недоступен снаружи | A/AAAA, firewall сервера и провайдера, NAT, свободные 80/443; localhost доступен только на самом сервере |
| `edge` не появился | В `.env` есть `COMPOSE_PROFILES=https`; команды выполняются в правильном каталоге |
| Сертификат не выпущен / `edge` unhealthy | Домен указывает на сервер, 80/443 доступны снаружи, исходящий ACME разрешён; подробная причина в логах `edge` |
| Сайт отвечает 502 | Состояние `api`/`db`, миграции и логи; после пересоздания API может потребоваться `docker compose restart web` |
| Регистрация отвечает ошибкой отправки письма | SMTP_HOST/PORT/USER/PASSWORD/FROM, STARTTLS, разрешённый отправитель и исходящий SMTP; без SMTP при `DEMO_MODE=false` регистрация не завершается |
| API сообщил об отправке, но письма нет | Спам/карантин и журнал почтового провайдера; принятие письма SMTP-сервером не гарантирует доставку во входящие |
| Ссылка ведёт на localhost / после входа снова форма | PUBLIC_URL, HTTPS и COOKIE_SECURE; после изменения `.env` пересоздайте сервисы командой запуска, одного `restart` для новых переменных недостаточно |
| Остались демопрофили | Это данные прежнего запуска: переключатель DEMO_MODE не очищает БД |

Перед передачей логов другим людям удалите секреты, персональные данные и ссылки с токенами.

### 7. Сохранение данных и обновление

Пользователи, профили и переписка находятся в томе `fsp_db`; сертификаты — в `fsp_tls_data` / `fsp_tls_config` (с префиксом Compose-проекта). Обычные перезапуск и пересборка сохраняют эти тома. **Не используйте `docker compose down -v` и очистку томов для обновления.** Не меняйте пароль БД в `.env` без отдельной процедуры смены пароля в PostgreSQL.

Перед обновлением сохраните дамп БД и отдельно защищённые копии `.env` и томов сертификатов. Пример создания дампа из каталога проекта:

```bash
umask 077
mkdir -p local-backups
FSP_BACKUP_PATH="local-backups/fsp-$(date -u +%Y%m%dT%H%M%SZ).dump"
docker compose exec -T db pg_dump -U fsp -d fsp -Fc > "$FSP_BACKUP_PATH"
```

Проверьте код завершения `pg_dump`; не считайте файл успешной резервной копией при ошибке. Копию храните также вне сервера с ограниченным доступом; восстановление следует проверять на отдельной БД.

Для обновления чистой рабочей копии:

```bash
git status --short
git pull --ff-only origin codex/fsp-mvp
docker compose up -d --build --force-recreate --no-deps --wait --wait-timeout 180 api web task-worker edge
curl --fail https://jobs.example.org/api/health
```

Если есть локальные изменения или `pull --ff-only` отказал, сначала разберите расхождение; не применяйте принудительный reset. Команда обновляет приложение и прокси при уже работающей БД; обновление самого PostgreSQL планируется отдельно. Обновление может кратковременно прервать работу сайта.

Запуск на публичном адресе не означает проверку любой нагрузки: границы измерений, резервирования и эксплуатации описаны в документах ниже. Это инструкция текущего MVP, а не заявление о сертификации или готовности к произвольному масштабу.
